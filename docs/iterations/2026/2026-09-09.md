## Reusable findings fed back into the template

The Engine pressure test exposed the following reusable test-baseline gaps:

1. `global.json` selects `Microsoft.Testing.Platform`, so generated test projects must use an MTP-compatible framework rather than an unspecified/legacy runner.
2. The standard template baseline centrally manages `Microsoft.NET.Test.Sdk`, `xunit.v3`, and `xunit.runner.visualstudio`; `xunit.v3` supplies the MTP-compatible xUnit framework while the other test packages support the template's VSTest/IDE compatibility baseline.
3. A newly initialized test project must contain at least one real test. Microsoft.Testing.Platform treats a zero-tests run as non-success, so an empty test project does not prove the CI pipeline.
4. Test code must still comply with the repository analyzer baseline; the initial smoke-test method name with underscores triggered CA1707 because warnings are treated as errors.
5. Bootstrap-only production code must not accidentally establish public API surface. Engine's assembly marker was made `internal`; this is an Engine-specific implementation lesson rather than a generic template requirement.

## Release closeout

The repository template has two different release-documentation concerns: the template repository's own version history and the clean release-management files inherited by generated repositories.

Decision:

- `CHANGELOG.md`, `TODO.md`, and `RELEASE_NOTES.md` remain clean seed files for repositories generated from the template.
- The repository-template's own release history is recorded in GitHub Releases.
- The `v0.1.0` GitHub Release description combines the template's release narrative, changelog, validation evidence, pressure-test results, and remaining TODO/future direction.
- The tag is created only after the release-closeout PR is merged and the final `main` commit is known.

During closeout, the two Copilot comments left on PR #11 were also reviewed. Their distinction between Microsoft.Testing.Platform framework support and VSTest/IDE compatibility tooling was valid. README and Architecture Check wording were clarified so `xunit.v3` is identified as the MTP-compatible framework while `Microsoft.NET.Test.Sdk` / `xunit.runner.visualstudio` are described as compatibility tooling included by the template baseline.

## Iteration logging policy update

A process gap was identified while moving between repository-template, Engine, and Abstractions work: daily iteration logs were being maintained, but some updates were occurring primarily at closeout rather than continuously as meaningful work happened.

The repository agent contract was tightened directly on `main` so that:

- today's iteration log is created or updated before substantive work;
- meaningful decisions, implementation results, validation outcomes, review findings, merges/releases, blockers, and architecture implications are recorded as they occur;
- repository work cannot be declared complete until today's iteration log has been explicitly checked for completeness;
- exactly one iteration log is maintained per repository per calendar day;
- today's work must never be appended to a previous day's log;
- when work spans multiple repositories, each repository maintains its own daily execution record.

Because the template `CHANGELOG.md` is a clean generated-repository seed, this template-policy clarification is recorded here rather than polluting that seed file with repository-template history.
